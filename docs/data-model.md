# Nest v1 data model

Models live in `app/models/`. Alembic migrations live in `migrations/`. Stream A owns both. Ask nest 1 for schema changes (see [Changing the schema](#changing-the-schema)).

```
workspaces ─┬─ workspace_bots         (0..1, the customer's BotFather bot)
            ├─ members ── telegram_users (global Telegram profile)
            ├─ invites
            ├─ projects ── tasks ─┬─ task_reminders (per-task override)
            │                     └─ task_events    (activity log)
            └─ notifications      (outbox → Telegram DMs)

better-auth (owned by the dashboard, never touched by Alembic): user, session, account, verification, jwks
```

## Conventions

- **IDs** are UUID v4, generated by Postgres (`gen_random_uuid()`). One exception: `telegram_users` uses the Telegram user id as its key. better-auth ids are text.
- **Timestamps** are `timestamptz`, stored in UTC. Display them in the workspace timezone (`workspaces.timezone`, IANA name).
- **Enums** are `varchar(32)` columns with a CHECK constraint, not native Postgres enums. Adding a value means swapping the constraint, not running `ALTER TYPE`. Python enums are in `app/models/enums.py`.
- **Constraint names** follow the naming convention in `app/models/base.py`, so migrations are deterministic.
- **Tenancy:** every tenant table has a `workspace_id`, including tables like `tasks` where it could be derived. Every query filters on it. Deleting a workspace cascades to everything it owns.

## Tables

| Table | Purpose | Notes |
|---|---|---|
| `workspaces` | Tenant | `owner_user_id` = better-auth `user.id`, with no FK because better-auth owns that table and it may not exist when migrations run. `reminder_lead_hours` defaults to 24. `next_task_number` is the counter behind task numbers. |
| `workspace_bots` | The workspace's own Telegram bot (1:1) | `token_encrypted` holds Fernet ciphertext (`TOKEN_ENCRYPTION_KEY`); never log it. `webhook_secret` is checked against `X-Telegram-Bot-Api-Secret-Token`. `status` is `active`, `invalid` (token revoked) or `disconnected`. A partial unique index stops a bot from being live in two workspaces, while a disconnected row doesn't block reuse. |
| `telegram_users` | Global Telegram profile cache | Upserted on every `/start` or update. |
| `members` | A person in a workspace | `role` is `manager` or `member`. `status` is `pending` (invited by @username, no `/start` yet), `active`, `unreachable` (blocked the bot, 403) or `removed` (soft delete, so task history keeps its assignee). Identity is any of `user_id` (dashboard account), `telegram_user_id`, or `invited_username`, and at least one is required. The workspace creator gets a `manager` row with `user_id` set and may link Telegram later. Unique on (workspace, telegram_user_id) and (workspace, user_id). `private_chat_id` is the DM chat with the workspace bot. `invite_id` records which link they joined through. |
| `invites` | `t.me/<bot>?start=<token>` links | `token` is at most 64 characters of `[A-Za-z0-9_-]` (Telegram's start-parameter limit). `max_uses` NULL means unlimited and defaults to 1. `use_count` is incremented on redeem. A link is valid when it isn't revoked, `expires_at > now()`, and `use_count < max_uses`. |
| `projects` | "Group" in the UX map | `status` is `active` or `archived`. A project can only be deleted when it has no tasks (the FK from `tasks` has no cascade). |
| `tasks` | Unit of work | One assignee (required) and one project (required). `status` is `pending` or `completed`, with no other states. A CHECK keeps `completed_at` set exactly when the task is completed. `completed_via` is `telegram`, `dashboard` or `system`. `number` is a short per-workspace number for `/done 12`. |
| `task_reminders` | Optional per-task reminder offsets (minutes before `due_at`) | If a task has no rows here, the workspace's `reminder_lead_hours` applies. |
| `task_events` | Activity log for task detail (C4) | `type` is `created`, `updated`, `reassigned`, `due_changed`, `completed` or `reopened`. `source` is `telegram`, `dashboard` or `system`. `data` holds the before and after values. |
| `notifications` | Transactional outbox for every Telegram DM | Insert in the **same transaction** as the change that caused it. `idempotency_key` is unique, which guarantees no duplicate sends (e.g. `assigned:{task_id}:{member_id}`, `reminder:{task_id}:{offset}`). The worker claims `status='queued' AND next_attempt_at <= now()` with `FOR UPDATE SKIP LOCKED`, using the partial index `ix_notifications_due`. `task_id` is SET NULL when the task is deleted, so `telegram_message_id` survives for editing the old DM. |

### Allocating a task number

Allocate the number in the same transaction as the insert:

```sql
UPDATE workspaces SET next_task_number = next_task_number + 1
WHERE id = :workspace_id
RETURNING next_task_number - 1;
```

The row lock serializes concurrent creates within a workspace. `uq_tasks_workspace_id_number` is the backstop.

### Removing a member

Members are never hard-deleted. Set `status='removed'` and `removed_at`, and reassign their *pending* tasks (`assignee_member_id` is required, per PRD 6.3). Completed tasks keep pointing at the removed member.

## Running migrations

```bash
alembic upgrade head        # uses DATABASE_URL (from .env)
alembic downgrade base
alembic check               # fails if models and migrations have drifted
alembic -x url=postgresql://... upgrade head   # one-off target
python scripts/seed.py [--owner-email you@example.com]   # dev data, idempotent
pytest tests/test_migrations.py                # round trip, drift, legacy DB, cascades
```

In production (Neon), migrations use the **direct** (non-pooled) connection string.

## Changing the schema

1. Ask Stream A (nest 1). Only Stream A edits `app/models/` and `migrations/`.
2. Edit the model, then run `alembic revision --autogenerate --rev-id 00NN -m "..."`. Review the file: autogenerate duplicates the enum CHECKs and doesn't handle circular FKs.
3. `alembic upgrade head && alembic downgrade -1 && alembic upgrade head`, then `alembic check` and `pytest tests/test_migrations.py`.
4. Merge it to `main` on its own, before the code that depends on it.

## Legacy data (decision: reset)

Pre-Alembic databases contain the old bot tables (`users`, `workspaces`, `members`, `projects`, `tasks`, `task_assignments`, `reminders`, plus the `taskstatus` enum) and the unused Prisma tables (`Workspace`, `Member`, `Project`, `Task`).

**Nothing is migrated.** Here's why:
- The old rows don't fit the v1 model. Tasks are keyed by Telegram group `chat_id`, have many assignees, and use NEW/IN_PROGRESS/DONE. Members belong to the one global bot. Workspaces have no owner and store a plaintext bot token.
- Every v1 workspace has to connect its own bot, and every member has to `/start` that bot through an invite link. So even migrated members would need re-linking.
- The local dev DB holds only test rows (8 tasks from March 2026).

**How it runs:**
1. `0001` moves any legacy tables into a `legacy` schema (`ALTER TABLE ... SET SCHEMA legacy`) before creating v1 tables with the same names. Nothing is deleted at this step, and `downgrade` moves them back.
2. `0002` runs `DROP SCHEMA legacy CASCADE`. This step is irreversible.

To keep a copy (e.g. the production Neon DB, if it has data worth keeping): `alembic upgrade 0001`, `pg_dump -n legacy`, then `alembic upgrade head`. On Neon, create a branch first; that's a free snapshot. Running this against production needs Zak's OK.

The better-auth tables are never moved, altered, or dropped.

**Heads-up for old code:** the legacy `models.py`/`database.py` call `create_all()` and `migrate_*()` at startup. Against a migrated DB they recreate `users`, `task_assignments`, and `reminders`, and then fail against the new `workspaces`/`tasks` shapes. Don't run the old bot against a v1 database. A1/B1 replace that code.
